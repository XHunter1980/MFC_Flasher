# MFC Module Flasher (MFC_Flasher) v1.97

Настольное GUI-приложение (PyQt6) для прошивки модулей многофункционального
контроллера (МФК / IskraIO). Автоматизирует полный цикл обновления прошивок:
загрузку агента и файлов на устройство, формирование и редактирование сценария
прошивки (СП), запуск прошивки, анализ результатов и выгрузку логов.

Связь с устройством:
- **SSH/SFTP** (paramiko) — работа с агентом `IskraIO_Util` в каталоге
  `/home/user/fw_update/` на устройстве;
- **HTTP API** (`/vx3/backend.fcgi`) — получение информации о модулях
  (запрос `IskraIOGetAll`) с двухшаговой авторизацией (token + SID).

## Основные возможности

> 📖 Краткое руководство пользователя (установка, рабочий процесс, редактор СП, автопрошивка, устранение неполадок) — в файле [docs/USER_GUIDE.md](docs/USER_GUIDE.md).

| Операция | Описание |
|---|---|
| **АВТОПРОШИВКА** | Полная цепочка без диалогов: внедрение агента и прошивок → создание СП → тихий редактор (автозаполнение appl + сохранение plan.xml) → прошивка → вывод результата по каждому модулю («с версии X на Y»). Директория агента на устройстве не удаляется |
| Внедрить агента и прошивки | Создание `/home/user/fw_update/images`, загрузка `IskraIO_Util` и файлов прошивок по SFTP с контролем формата имён (режимы детализации лога) |
| Создать СП | Остановка сервисов телемеханики, запуск `IskraIO_Util MakePlan`, запуск сервисов (ожидание 20 с) |
| Импортировать СП | Загрузка локального `plan.xml` на устройство (с бэкапом текущего) |
| Экспортировать СП | Выгрузка `plan.xml` с устройства |
| Запустить прошивку | `IskraIO_Util Update` с индикатором прогресса по актуальному plan.xml на устройстве, выгрузка `operation.log`, анализ `result.txt` |
| Просмотр результата | Окно результатов: дата/время прошивки, статус («Выполнено»/ошибка), версии до/после по каждому слоту; кнопка выгрузки дампа |
| Удалить агента | Удаление каталога `/home/user/fw_update/` с контроллера (выполняется вручную) |
| Выгрузить дамп | Выгрузка `io.can.box2.csv` с устройства |
| Редактировать СП | Диалог редактирования сценария: выбор модулей, путей и типов прошивок (appl/boot), автозаполнение appl/boot, флаг «Не прошивать при совпадении версий», валидация имён файлов и версий |
| Информация о модулях | Таблица модулей через HTTP-бэкенд (тип, серийный номер, версии FW/HW) |

## Требования

- Python 3.9+
- PyQt6, paramiko (см. `requirements.txt`)
- Сетевой доступ к МФК по SSH (root) и HTTP

## Конфигурация

Параметры подключения и пути задаются в окне приложения и сохраняются в
`mfc_flasher_config.json` рядом с запускаемым файлом:

| Ключ | Описание |
|---|---|
| `ip` | IP-адрес МФК |
| `password` | Пароль пользователя root (SSH) |
| `agent_dir` | Путь к **файлу** агента `IskraIO_Util` (в его директории выгружаются логи/дампы) |
| `firmware_dir` | Директория с файлами прошивок (сканируется рекурсивно, включая подпапки full/appl/boot) |
| `plan_xml` | Локальный файл сценария прошивки |
| `format_control` | «Контроль формата прошивок» (по умолчанию `true`): файлы с некорректными именами и формат `full` на устройство не загружаются и прошивка ими запрещена; при `false` — только предупреждения |
| `log_detail` | «Детализация» операционного лога (по умолчанию `false`): в кратком режиме скрыты HTTP-Payload, заголовки и тело ответа, MakePlan stdout; при включённой — показываются имена всех загружаемых и игнорируемых прошивок |

> ⚠️ **Внимание:** `mfc_flasher_config.json` содержит пароль root и **не должен
> попадать в репозиторий** — он добавлен в `.gitignore`.

## Формат имени файла прошивки

Имя должно начинаться с префикса типа образа: `appl_`, `boot_` или `full_`.

Полный (строгий) формат распознаётся парсером полностью:

```
<prefix>_<МАРКЕР>_<ТИП>[_...]_R<мажор>[_|.]<минор>_<ДДММГГ>.bin
примеры: appl_atb3500_dir12_R3_4_191026.bin
         full_atb3500_ai8_AI8R_R3_0_270625.bin
```

- версия допускается в виде `R3.4` или `R3_4`; дата — 6 цифр `ДДММГГ`;
- `PSU` нормализуется в тип `POWER_UNIT`; маркеры вида `ATBxxx` приводятся к `ATB xxx`;
- короткие имена с корректным префиксом (`appl_atb3500_dir12_r.bin`) допускаются к
  загрузке и прошивке, но при включённом контроле формата считаются некорректными
  (парсер не извлекает из них версию);
- формат `full` пока не поддерживается для прошивки (при отключённом контроле
  загрузка на устройство возможна с предупреждением);
- файлы без префиксов `appl_/boot_/full_` игнорируются с предупреждением в логе.

Файл сценария прошивки (`plan.xml`) использует корневой элемент `<Root>` и
значения типа образа `appl` / `boot`:

```xml
<?xml version='1.0' encoding='utf-8'?>
<Root><Image module_slot="4" module_type="DIR12" path="images/appl_atb3500_dir12_R3_4_191026.bin" type="appl" /></Root>
```

### Архитектура кода (один файл)

- `SSHClient` — обертка над paramiko (exec, sftp get/put/chmod/stat/listdir);
- `BackendClient` — HTTP-клиент бэкенда (`/vx3/backend.fcgi`, фиксированный путь):
  `get_token` → запросы с token/SID, повтор при протухшей сессии (`result == 2`) и
  ошибке `result == 106` (пауза 10 с, не более 3 попыток), отладочный
  лог в `http_debug.log`;
- `parse_plan_xml`, `parse_result_txt`, `parse_firmware_filename`,
  `normalize_fw_version` — разбор данных и имен файлов; `analyze_operation_log` —
  различение «успех / ошибка / нет информации» по operation.log устройства;
- `OperationWorker (QThread)` — выполнение операций 1–13 вне GUI-потока,
  сигналы `log_signal` / `progress_signal` / `finished_signal`; параллельный
  запуск операций заблокирован (кроме выгрузки дампа из окна результатов);
- `ModuleInfoDialog`, `ViewResultDialog`, `EditSPDialog` — диалоги;
- `MainWindow` — форма, конфигурация, журнал операций (цветная подсветка:
  служебные строки начала/завершения операций — синим, ошибки — красным),
  цепочка «АВТОПРОШИВКА» (шаги 1→2→11(tихий appl)→6) с локальной копией result.txt.

## Рабочий процесс (типовой цикл прошивки)

1. Указать IP, пароль, файл агента и директорию прошивок.
2. **Внедрить агента и прошивки** (операция 1).
3. **Создать СП** (операция 2) — остановит телемеханику, выполнит `MakePlan`,
   запустит сервисы и подождёт 20 с.
4. При необходимости — **Редактор СП** (операция 9): автозаполнение appl/boot,
   выбор прошивок, флаг «Не прошивать при совпадении версий», сохранение
   `plan.xml` на устройство (пустой план сохранить можно — выбор не обязателен).
5. **Запустить прошивку** (операция 6) — проверяет наличие актуального плана,
   агента и всех файлов прошивок на устройстве.
6. **Просмотр результата** (операция 8) — дата/время, статус «Выполнено»,
   версии до/после; кнопка «Выгрузить дамп» в этом окне.
7. По завершении работ — **Удалить агента** (операция 12) вручную.

Быстрый путь — **АВТОПРОШИВКА** (операция 13): шаги 2–6 выполняются одной
цепочкой без диалогов, результат по каждому модулю выводится в операционный лог.

## Разработка: линтер и CI/CD

### Линтер ruff

Конфигурация — в `pyproject.toml` (раздел `[tool.ruff]`). Проверка стиля (E/W),
потенциальных багов (F, B — flake8-bugbear), порядка импортов (I), современного
синтаксиса (UP). Ряд правил отключён с обоснованием в комментариях конфига
(обработка исключений в фоновых потоках, длинные строки CSS/User-Agent).

```bash
pip install ruff
ruff check .          # проверка
ruff check --fix .    # автоисправление безопасных замечаний
```

### GitHub Actions

- **CI** (`ci.yml`) — при каждом push/PR в main: `py_compile`, `ruff check .`,
  установка зависимостей из `requirements.txt` и проверка их импорта.
- **Build Windows EXE** (`build-exe.yml`):
  - ручной запуск (Actions → *Build Windows EXE* → *Run workflow*) — собирает
    `MFC_Flasher_v<VER>.exe` (версия из `APP_VERSION`) на windows-latest и складывает его в Artifacts;
  - **push тега `v*`** (например `v1.60`) — автоматически собирает `.exe` и
    публикует **GitHub Release** с вложенным `MFC_Flasher_v<VER>.exe` и заметками,
    сгенерированными из истории коммитов.

Выпуск релиза:

```bash
git tag v1.97 -m "MFC_Flasher v1.97"
git push origin v1.97   # Actions соберёт exe и создаст Release
```

## Примечания и известные ограничения

- Все операции выполняются от пользователя **root** по SSH; используйте только
  в доверенной сети. Используется `AutoAddPolicy` (ключи хостов не проверяются).
- HTTP-API работает по незащищенному `http://` — это особенность устройства.
- Отладочный лог `http_debug.log` пишется в текущую директорию при каждом
  создании `BackendClient` (перезаписывается).
- Операции «Создать СП» и «Прошивка» останавливают сервисы `PrjA.service` и
  `PrjA-tele.service` и гарантированно перезапускают их в `finally`.
